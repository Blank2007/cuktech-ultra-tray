# 控制指令实测记录（酷态科 10 号 Ultra）

本文件记录**在这台真机上实测验证过**的控制能力，用来支撑托盘程序的控制页。
每条结论都写明实测手段与观测到的原始字节；没试通、或者根本没试的项目集中在最后一节，**不要把它当已知结论用**。

- 设备：CUKTECH 10 Ultra，MAC `AA:BB:CC:DD:EE:FF`，固件 `2.1.2_0073`
- 通道：BLE + 米家 mible 帧（GATT `0x001a` CmdSend / `0x001b` CmdRecv），token 认证后走 MIoT 命令
- 工具：`src\probe-cs` 的 `ctl` 子命令（本轮新增），形如
  `probe-cs ctl --mac <MAC> --token <24位hex> -- get:16 set:16:0x0b ports:1`
  步骤用空格分隔，`get:piid` / `set:piid:value`（value 可写 `0x..`）/ `ports:轮数`（读四口）/ `sleep:毫秒`
- 实测时间：2026-11-17 17:13 – 17:17（同一台设备、同一供电环境）

## 1. 一条命令的通用形态（实测）

**读**：`GET siid=2, piid=<P>` → 回帧 `op=0x03`（GET 结果），带值，`err=0x00`。

**写**：`SET siid=2, piid=<P>, value=<V>` → 回帧 `op=0x01`（SET ACK），`raw=<空>`，**不含新值**。

真实抓到的两行：

```text
[get] 17:16:32.554 siid=2 piid=16 -> op=0x03 err=0x00 type=16 raw=0d u32=13
[set] 17:16:34.814 siid=2 piid=16 value=15 (0xf) -> op=0x01 err=0x00 type=0 raw=<空> u32=-
```

由此得到两条**必须写进代码**的规矩：

1. **SET 的 `err=0x00` 不能当成功凭证**。设备对所有写入都回 `op=0x01 err=0x00`，包括它其实会偷偷改掉的值（见 `2.4 越界钳制）。
2. **SET 不回显新值**，所以每次写之后必须再 `GET` 一次回读，只有「回读 == 请求值」才算成功；回读失败要如实报「实际状态未知」，不能按 0 兜底。

## 2. 端口开关（SIID=2, PIID=16）—— 控制页的核心

### 2.1 位定义（四个位逐位实测）

`port_switch` 是 4 位位掩码。**逐位单独关掉、再看四口读数**的实测结果：

| 写入 | bit 含义验证 | 断电的口 | 该口断电后的读数 |
|---|---|---|---|
| `0x0F`（基线） | 全通 | — | C1 `010a02c9` 20.1V、C3 `11300433` 5.1V |
| `0x0E` 清 bit0 | bit0 = C1 | **C1** | C1 `00000000` |
| `0x0D` 清 bit1 | bit1 = C2 | **C2** | C2 `00000000` |
| `0x0B` 清 bit2 | bit2 = C3 | **C3** | C3 `00000000` |
| `0x07` 清 bit3 | bit3 = A | **A** | A `00000000` |

结论：**bit0=C1，bit1=C2，bit2=C3，bit3=A**（和参考实现一致，本轮逐位确认过）。恢复写 `0x0F` 后对应口立即恢复读数。

### 2.2 必须「读-改-写」

因为一次写入就是整台设备的全部四路开关，改一个口必须基于当前值算新值。实测流程（已封装进 `DeviceClient.SetPortEnabledAsync`）：

1. `GET 2/16` 拿基线 `mask`（**失败就中止**，绝不能按 0 兜底——那会把另外三个口一起关掉）
2. 按位运算得到 `newMask`（0x00–0x0F）
3. `SET 2/16 = newMask`，超时给 6s
4. 立刻 `GET 2/16` 回读，回读值 ≠ 请求值 → 报「设备只接受了 0x..」
5. 回读成功 → 更新本地缓存与界面

### 2.3 写入后确实断电（不是只改标志位）

`0x0B`（C3 关）实测前后：

```text
[set] siid=2 piid=16 value=11 (0xb) -> op=0x01 err=0x00 raw=<空>
[get] siid=2 piid=16 -> op=0x03 err=0x00 type=16 raw=0b
[ports] C1[010a03c9]20.1V/0.30A/6.0W C2[00020000]idle C3[00000000]idle A[01600433]5.1V/0.40A/2.0W
```

C3 的负载功率（5.1V/0.40A/2.0W）在关断后**直接归零**，所以是真断电。恢复后同一负载重新出现在 C3。

### 2.4 越界值被静默钳制（重点）

| 写入 | SET ACK | GET 回读 |
|---|---|---|
| `0x1F` | `op=0x01 err=0x00`（"成功"） | **`0x0F`** |
| `0xFF` | `op=0x01 err=0x00`（"成功"） | **`0x0F`** |

设备不报错、不拒绝，只是把值按低 4 位掩到 `0x00–0x0F`。所以：
**界面层要自己校验 0x00–0x0F；而且回读校验不能省**，否则「ACK 成功」会被当成「写进去了」。

### 2.5 变化推送（PIID16）

开关变化后设备会推 `siid=2 piid=16 op=0x04` 的**空值**推送；四口也会推 `piid=1..4` 的 1–2 字节短帧（如 `04`、`0533`）。

- 推送**不带新值**，只能当「有东西变了，快去读一次」的提示；
- 面板/控制页收到推送后应主动 `GET` 一次，而不是拿推送字节当数据用。

### 2.6 断开重连后开关状态保持

`SET 0x0D`（关 C2）→ 结束进程（BLE 断开）→ 新进程重新连接 → `GET 2/16` 回读 **`0x0D`**，C2 仍 `00000000`。

即：**开关状态存在设备里，跨 BLE 连接保持**（本轮只验证了「断开重连」，**没有验证整机断电重启后是否保持**——那需要拔电，未做）。

### 2.7 关断态与空载态的区分（判读要点）

同一个口两种「看起来没功率」的情况，原始 4 字节完全不同：

| 情况 | 原始字节 | 说明 |
|---|---|---|
| 口开着、空载 | C2 `00020000`、A `00300000` | 第 1 字节 state=0x00，**第 2 字节 code 非 0** |
| 口被关断 | `00000000` | 4 字节全 0 |

所以：**4 字节全 0 = 该口断电**；`code` 非 0 = 该口通电。控制页请用「port_switch 位 + 全 0 判据」双重判断，不要只看功率为 0。

### 2.8 已知的读数怪癖（C3 / A 会串读数）

- 关掉 C3（`0x0B`）时，**A 口**会冒出 `01600433` / `01600533`（5.1V、0.4–0.5A）；C3 恢复后 A 又回 `00300000`。
- 关掉 A（`0x07`）时，**C3 口**会冒出 `01800011`（1.7V）→ `01800033`（5.1V）；A 恢复后 C3 回到 `00300000`（注意：C3 上原本的负载读数在那一瞬间变成 0）。

推测是「C3/A 共用一路功率计，关掉其中一个时另一个的采样被残留电压串到」。**结论：某一路的真实功率不要只看它自己的 4 字节，判断通电与否以 port_switch 位为准**；这是固件行为，本轮没有进一步深挖。

## 3. 其它实测通过的写入项

以下四项都做了「写 → GET 回读 → 写回原值」的完整往返，回读值与请求值完全一致。

### 3.1 场景模式 PIID=5
取值 1=AI、2=数码生态、3=单口、4=均衡。**四档全部实测往返**（2026-11-22，固件 2.1.2_0073）：
基线 `0x03`（单口）→ 写 `0x01` 回读 `0x01` → 写 `0x03` 回读 `0x03` → 写 `0x04` 回读 `0x04` →
写 `0x02` 回读 `0x02`，最后写回 `0x03`。此前（更早那轮）只验过 2↔3 的往返。

> GET 回帧是 `op=0x03 type=16 raw=03`（1 字节），`MiotMessage.UIntValue` 需要 ≥4 字节所以拿不到值，
> 必须读 `ValueBytes[0]`。读成 0 的话界面会一直显示「不知道当前是哪档」，而设备其实回的是 3。

### 3.2 息屏时间 PIID=6
基线 `0x05`（1 分钟）。写 `0x01` → 回读 `0x01`；写回 `0x05` → 回读 `0x05`。
取值 1=5min、2=10min、3=30min、4=常亮、5=1min。

### 3.3 语言 PIID=13
基线 `0x01`（中文）。写 `0x00` → 回读 `0x00`；写回 `0x01` → 回读 `0x01`。

### 3.4 USB-A 小电流 PIID=15、空闲息屏 PIID=19、屏幕方向锁 PIID=20
这三个都是 1 字节，`0/1` 往返全部回读一致：
- 15：0 → 1 → 0，回读同步；**但没有插设备观测到 USB-A 真的进入小电流模式**，所以只能说「命令被设备接受并保存」，行为效果未验证。
- 19：基线 1，写 0 回读 0，写回 1 回读 1。
- 20：基线 0，写 1 回读 1，写回 0 回读 0。

> 这三项的 GET 回帧 `type=0` 且只有 1 字节（`MiotMessage.UIntValue` 需要 ≥4 字节，拿不到值），解析要直接读 `ValueBytes[0]`。PIID16 回帧是 `type=16` 的 1 字节（`raw=0d`），同理。

## 5. 工程注意事项（踩过的坑）

1. **BLE GATT 同一时刻只能被一个进程持有**。托盘程序（CuktechTray.exe）在跑的时候，probe-cs 连接会失败：
   `!! 失败: InvalidOperationException: 枚举特征失败: AccessDenied`
   测控制命令前必须先退出托盘程序；这也是控制页必须做在**同一个进程内**（共用同一个 DeviceClient 会话）的原因。
2. **同一个 mible 会话内命令不能交错**。写命令（GET 基线 → SET → GET 回读）必须整段独占，否则轮询的 GET 会插进来。实现里用一把 `SemaphoreSlim` 把「四口轮询」和「写命令」串起来。
3. **SET 超时给足**：实测 SET 的 ACK 常在 300ms 内到，但认证后首帧偶发慢到 1s 以上，代码里 SET 用 6s、GET 用 4s、轮询单口 2.5s。
4. **认证后才可下发命令**（`MibleSession.Authenticated`）。未连接/未认证时控制页应禁用所有开关，并提示「还没连上充电器」。
